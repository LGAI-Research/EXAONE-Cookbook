# 단일 ToolAgent vs 멀티 롤 — 무엇을 언제 쓸까

> Track 06 Session 3 의 측정(지연·품질·정답률)에 근거한 결정 가이드. 팀 wiki 에 붙여 쓰세요.

## 기본값: 단일 ToolAgent

대부분의 작업은 단일 ToolAgent 로 충분합니다 — **빠르고**, 잘 명세된 작업이면 멀티 롤과 **품질이 같습니다**.

- 도구 경로가 분명한 작업(정책 조회, 환율 변환, FAQ).
- 잘 명세된 산출물(필요한 항목이 프롬프트에 다 있는 메모) — Session 3 Part A 에서 single 과 multi 의 커버리지가 동일.
- 지연·비용 예산이 빡빡할 때.

## 멀티 롤(executor → verify → revise)을 쓸 때

검증 단계가 **실제로 잡을 게 있을 때만** 멀티 롤의 추가 지연이 값을 합니다.

- **출력이 검증 가능하고, 틀리면 비용이 큰 작업** — 정산·집계·계산. Session 3 Part B 에서 single 은 산술을 가끔 틀려도 검증 없이 ship 하지만, 결정적 검증기를 둔 멀티 롤은 그 오류를 잡아 보완을 시도하고 다시 검증 → 모든 출력이 검증을 거침.
- **계획 + 초안 + 독립 검수**가 필요한 산출물(규정 메모, 컴플라이언스) — 생성자와 검수자의 역할·권한을 분리.
- **단계별 감사 추적**이 필요할 때(`workflow_trace.json` 처럼).

## 핵심 원칙

- 멀티 롤의 가치는 "더 똑똑한 생성"이 아니라 **독립 검증**입니다. 검증기가 **결정적**(파이썬 재계산·스키마 검사)일수록 신뢰성이 높습니다 — LLM 검수자만으로는 흔들립니다.
- 모델의 **능력 격차**(예: 산술)는 멀티 롤이 아니라 **도구**(계산기)로 메웁니다. 멀티 롤은 그 위에 "검증·보완"을 더하는 것.

## 비교 신호 (이 노트북)

- `comparison.json` 의 `part_a_well_specified` — single·multi 의 `quality` 가 같고 `latency_ms` 만 multi 가 큼 → single.
- `comparison.json` 의 `part_b_calculation` — single 은 검증 없이 ship(틀려도 모름), multi 는 결정적 검증기로 매 출력 확인 → 틀린 답의 비용이 큰 작업에선 multi.
